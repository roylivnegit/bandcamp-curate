## 3 · Design

**[architect] ADR-0003**

- _title_: ADR-0003 — Bounding the co-owner weight (amends ADR-0002)
- _problem_: ADR-0002 landed on branch commit 2c1c2ed and never merged. Its weight is sum(1 + overlap(f)) over co-owning fans — unbounded and linear in overlap. Roy owns ~1,700 items, so one neighbour with overlap 200 contributes 201 and outscores fifty distinct co-owners who each share two records (50 x 3 = 150). That inverts the goal: the score stops meaning "many people close to my taste own this" and starts meaning "one whale owns this". Two things follow from the same unbounded numerator. W_TAG_AFFINITY = 0.25 (engine.py:45) was calibrated against a raw fan count in the single digits and can never break a tie against a numerator in the hundreds, so the tag term is silently retired. And crawl progress contaminates the numerator, not only the denominator ADR-0002 argued about: a collection visit spends at most PAGES_PER_VISIT = 10 pages and parks the rest (crawl/service.py:70, frontier.mark_partial), so a fan paged ten deep carries more measurable overlap than one paged once, and linear weighting passes that 10x straight into the score. Separately, ADR-0002's proposal text is wrong that merging is a no-op: curation_min_co_owners = 1 is, curation_weighted_co_owners = True is not, so the next recompute re-ranks the existing ~1,600-item feed.
- _approach_: Same seam as ADR-0002 — everything stays inside compute_recommendations; no caller threads a value, so the mid-crawl feed and the finalized feed rank identically. Two edits. (1) Damp the per-fan term: 1 + overlap becomes 1 + log1p(overlap). Still a numerator, still no denominator, still >= 1 per co-owner, so weighting still cannot drop a candidate to zero. Damped weights: overlap 0 -> 1.00, 2 -> 2.10, 20 -> 4.04, 40 -> 4.71, 200 -> 6.30, 1700 -> 8.44. Fifty co-owners at overlap 2 now score 105 against the whale's 6.3, where the branch as written had the whale win 201 to 150. Sublinearity is also the defence against the crawl-progress amendment: a fan crawled 10x deeper carries at most ~1.6x the weight, not 10x. (2) Bound the tag term in the same diff: score = W_CO_OWNER * co_owner_weight + W_TAG_AFFINITY * log1p(tag_affinity), with W_TAG_AFFINITY set so the tag term can never outweigh a second real co-owner. Note the reason a constant alone cannot fix this: tag_affinity is sum(tag_profile[t]) where tag_profile counts Roy's own owned albums per tag (engine.py:198-209), so on 1,700 albums a common genre is already in the hundreds — the "tag affinity breaks ties" comment at engine.py:43 is already false on main, before this diff. reasons["tag_affinity"] keeps its raw meaning; only the scoring is damped. Everything else is ADR-0002 unchanged: floor applied after exclusions, one helper and one counter across both loops, settings read at one edge, stats_out merged into scan.stats.
- _invariants_:
    - Every invariant in ADR-0002 still binds and is re-checked: build_exclusions untouched; floor applied after the exclusion and exclude_seed_tags checks and before sort/one_per_band; one floor helper and one counter shared by the album and track loops; the floor tests the raw distinct-fan count, never the score; no denominator anywhere in the weight; overlap computed over owned items only (is_wishlist false) and never including me; grep -rn curation_min_co_owners returns only app/config.py and app/curation/engine.py; no module-level accumulator; no migration file added; nothing in the diff can spend a Nimble credit.
    - No unbounded per-fan term: the weight expression contains log1p (or an explicit cap), and a bare `1 + neighbour_overlap.get(...)` appears nowhere.
    - Per-fan weight is monotone and bounded in a stated range: non-decreasing in overlap, >= 1.0 at overlap 0, and <= 1 + log1p(size of Roy's collection). Asserted numerically, not in prose.
    - Many beats one: on a corpus where the whale's overlap is 100x a tight neighbour's, fifty tight co-owners still outrank the item only the whale owns. This is the invariant 2c1c2ed violates today; a test that passes only because both fixtures are small does not satisfy it.
    - The tag term cannot outrank a co-owner: with an extreme tag_profile (one tag on 500 owned albums), a 1-co-owner item carrying that tag ranks below a 3-co-owner item carrying no matching tag.
    - Sublinear in crawl depth: multiplying one neighbour's overlap by 10 moves that neighbour's contribution by less than 2x. Asserted directly on the weight helper, so it does not depend on corpus shape.
    - Parity is still exact: weighting off at floor 1 reproduces main's ids, order and scores. Damping changes only the weighted path.
    - Weighting on at floor 1 is still membership-neutral: identical id set to the parity run, different order. This is what makes 'on by default' defensible.
    - reasons['tag_affinity'] is the raw sum, not the damped value, exactly as reasons['co_owners'] stays the raw distinct-fan count next to the new co_owner_weight key. Add keys; never redefine one.
    - The PR body states in one sentence that merging re-ranks Roy's existing feed, and names CURATION_WEIGHTED_CO_OWNERS=false as the runtime way back. Any moved assertion in test_curation.py is named and justified there.
